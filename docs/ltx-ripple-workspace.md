# LTX Ripple workspace

LTX Ripple (First Frame All Frames) is a separate LTX 2.5 video-edit workspace. A user chooses a source clip and a replacement first-frame image. The workspace previews both, shows the processed span, and sends a ComfyUI graph that propagates the first-frame change through the source motion. The original clip stays intact.

The graph follows the [creator's model card](https://huggingface.co/WepeNerd/LTX-Ripple) and [example workflow](https://huggingface.co/WepeNerd/LTX-Ripple/blob/main/Workflow_example/LTX_Ripple_FFAF_Edit_v11.json): source frames at 24 fps, replacement image prepended to the source frames, `LTXAddVideoICLoRAGuide` at frame 0, Ripple LoRA at default strength 1.35, 8-step simple sampling, `LTXVCropGuides`, and video output. The optional prompt defaults to the creator's preservation instruction. Source audio is passed through to the output.

Single-pass Ripple offers 5, 10, 15, and 20-second presets, plus a custom 2–20-second duration. LTX requires `8n + 1` output frames; the edited image occupies frame 0 and the rest come from a normalized 24 fps source segment. The UI shows the exact output frame count and disables spans that exceed the source. Longer single passes use tiled IC-LoRA guide encoding and may still exceed available VRAM.

ComfyUI normally limits uploads to 100 MB. The desktop bridge reads the server's `/features` upload limit and, when a video would exceed it, converts that source with FFmpeg to a uniquely named H.264/AAC MP4 at 24 fps. It keeps the source dimensions (padding an odd edge by one pixel) and checks that an already-24-fps Ripple source has the same frame count. Uploads stream from disk, and the temporary conversion is deleted afterward. If a clip cannot fit at usable bitrate, the app asks for a shorter source or a higher ComfyUI `--max-upload-size` setting.

Long video mode processes a 2-second to 5-minute source in sequential 5, 10, or 15-second chunks. Each following chunk uses a frame from the previous edited output at the overlap boundary as its replacement first frame. The user selects a 0–2-second overlap and can blend overlapping video with FFmpeg or trim the overlap and join. The original source audio is retained in the assembled MP4. A batch needs the app to stay open until assembly completes; completed chunk MP4s remain in the Ripple output folder if a later chunk fails or the batch is cancelled. The result depends on the model maintaining edit identity across chunks, so blends reduce seam visibility but cannot guarantee a seamless model transition.

Ripple and Photo Edit share one output resolution choice: Balanced (768-pixel longest side), Detailed (1024), nearest 32-pixel-aligned source size, or custom dimensions from 256 to 2048 pixels per side. Both source video frames and the replacement image are scaled and center cropped to the chosen size. Sending a frame to Photo Edit carries that size; returning an edited image carries its actual dimensions. The workspace shows any resampling before a Ripple render. Above 1024 pixels, the UI warns about GPU memory use.

Live preview can use the standard decoded frame or, when ComfyUI-KJNodes exposes `LTX2SamplingPreviewOverride`, the LTX sampling stream. Ripple output resolution and preview selection are saved in its draft. The rendered MP4 is resolved from Ripple's `SaveVideo` node 29, which prevents ComfyUI's `LoadVideo` node 9 from being mistaken for the result. Completed jobs saved by older app versions are checked against node 29 when the app reconnects.

Advanced controls include the Ripple LoRA strength and a separate source-motion guide strength (`LTXAddVideoICLoRAGuide.strength`). Both default to the creator's full guidance settings; lowering the motion guide permits more departure from the source and can reduce continuity.

The UI reports missing models, nodes, media, and connection. Workspace inputs are stored under a Ripple-specific key; render jobs use a separate provider ID. Model download and installation remain manual through the existing ComfyUI model setup. The [Ripple model card](https://huggingface.co/WepeNerd/LTX-Ripple) documents the first-frame propagation behavior and its limitations; the [creator's demo](https://huggingface.co/spaces/WepeNerd/ltx-ripple-demo/blob/main/app.py) currently caps its public UI at 5 seconds. Lightricks' [LTX 2.5 workflow guide](https://github.com/Lightricks/ComfyUI-LTXVideo/blob/master/example_workflows/2.5/README.md) documents the `8n + 1` frame rule and IC-LoRA workflow family. Longer Ripple passes and chunking here are application features, not a guaranteed capability of the public demo.
